    고가용성 · 장애 대응

    • 장애 자동 전환(failover) — PC 장애 시 Cloudflare Worker가 연결 실패·엣지 오류·1.5초 무응답을 감지해 요청 단위로 클라우드 대기 Pod(웜 스탠바이)에 재전송. 전환 순간 최대 응답 약 1.6~1.8초로, 예비 수단인 CNAME 전환(유예 60초 + DNS 반영)보다 빠르게 복구. 터널은 붙어 있는데 PC가 멈춘 경우(502)도 장애로 판정.
    • 장애 중 읽기·쓰기 보존 — 읽기는 PC 정상 시 저장해 둔 Cache API 사본으로 응답하고, 쓰기(POST)는 Durable Objects 큐에 보관했다가 PC 복구를 확인한 뒤 받은 순서대로 재전송(Idempotency-Key 포함). 장애 직후 첫 요청처럼 판정이 애매한 경우도 재확인 후 큐에 보관.
    • 에이전트 복구 — 에이전트가 재시작돼도 앱 슬롯·DB 터널·버스팅·스키마 상태를 다시 붙여 공개 주소가 끊기지 않게 하고, RDS 터널이 끊기면 자동 재연결. 컨트롤 플레인이 잠시 끊겨도 진행 중인 작업이 바로 실패하지 않도록 처리.
    • 하이브리드 컨트롤 플레인 — 클라우드와 온프레미스 에이전트를 WebSocket으로 연결해 토큰 인증·명령 중계·DB 터널 인증서 발급을 중앙에서 관리. Cloudflare API는 플랫폼이 에이전트 대신 호출해 에이전트에 클라우드 자격 증명을 두지 않음.

    거점 이전 · 확장

    • 거점 전환·클라우드 간 이전 — 앱을 PC↔클라우드, AWS↔GCP로 옮길 때 DB를 함께 이전(PC↔RDS는 SSH 리버스 터널, 클라우드 간은 PostgreSQL 복사). 이전 중에는 앱 쓰기를 멈췄다 다시 열어 데이터 정합성을 지키고, DB 없는 앱은 다운타임 없이 이전. 진행 단계 표시·취소와 버스팅과의 동시 실행 차단.
    • 멀티클라우드 동시 운영 — 같은 앱을 AWS·GCP에 함께 띄우고 엣지 Worker가 설정 비율대로 요청을 분산. DB는 GCP Cloud SQL 하나에 두고 AWS 쪽은 DB 릴레이로 접속. 한쪽이 502/503/504를 내면 GET은 반대쪽으로 재전송.
    • 클라우드 버스팅 — PC 부하가 임계치를 넘으면 연결 단위가 아니라 요청 단위로 초과분만 클라우드로 분산. 클라우드로 넘긴 유휴 keep-alive 연결은 회수하고, 대기 Pod를 유지해 기동 지연 없이 흡수.

    DB · CI/CD

    • 멀티테넌트 DB 프로비저너 — 공용 RDS에 프로젝트별 DB·계정 생성을 자동화, 테넌트 격리·연결 수 제한. DB 비밀번호는 SSM Parameter Store(SecureString·KMS)에 두고 플랫폼 메타데이터에는 참조 경로(secretRef)만 저장. 워커에 권한을 주면 사용자 앱이 다른 테넌트 비밀번호를 읽을 수 있어, SSM 접근 권한은 컨트롤 노드에만 부여해 노드 단위로 권한 경계를 나눔. Terraform으로 관리.
    • Expand-Contract 패턴 기반 무중단 스키마 마이그레이션(pgroll) — 구·신 버전 앱이 함께 동작하도록 스키마를 단계적으로 확장·정리하고, 실패 시 앱과 스키마를 함께 롤백. 두 버전 동시 운영을 깨는 연산은 적용 전 거절하고, 카나리 실패 시 시작한 마이그레이션을 즉시 되돌림. 온프레미스(내 PC) 배포에도 동일 적용.
    • 빌드 설정 자동 감지·배포 — 레포 파일에서 포트·DB·헬스체크 경로를 자동 감지해 Dockerfile을 생성하고, 백엔드+프론트를 Caddy 뒤 단일 이미지로 번들. GitHub → Kaniko → ECR → 블루그린, 전환 전 30초 카나리로 오류율·p95를 검증. 온프레미스는 20%씩 전환하며 새 슬롯의 5xx가 늘면 되돌림. 배포 실패 시 규칙·AI로 원인을 진단해 설정을 고쳐 최대 3번 재배포.

    리뷰 파이프라인

    • 정적 분석 (1차) — GitNexus 의존성 그래프로 변경 심볼의 호출자·피호출자·영향 경로를 추적하고, Codex가 diff·레포 전체·그래프를 함께 보고 bug·security·performance·dependency·policy 후보를 최대 5건 생성. 모든 지적에 실제 file:line 근거를 요구하고 존재 여부를 검증.
    • 재현·검증 (2차) — 후보를 테스트 DB의 transaction.atomic() 안에서 Django view·ORM을 직접 호출해 재현하고 expected/observed로 판정한 뒤 강제 롤백. 불확실하면 재현 스크립트를 자동 수정해 1회 재실행.
    • 분류 — 재현·검증 성공은 "재현된 문제", 미재현은 "재현하지 못한 발견", 재현했지만 반증 검토에서 탈락한 것은 "2차 검증 미채택"으로 나눠 PR 댓글에 게시. 한 번 안 걸렸다고 지적을 삭제하지 않음.

    안전 · 설계

    • 권한 최소화 — pull_request_target 신뢰 워크플로에서 동일 저장소 PR만 처리하고, PR 코드는 실행하지 않고 base만 가져옴. 리뷰는 읽기 전용 샌드박스, Gitea 토큰은 댓글 단계에서만 사용. 승인·머지·푸시·브랜치 보호 변경은 하지 않는 1차 리뷰어.
    • 재현 결과를 head SHA에 바인딩(evidence.json)해 같은 커밋의 결과를 보존. 런타임 의존성 없이 Python 표준 라이브러리만 사용.
